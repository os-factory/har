HAR 1.0.0 changes one thing, and everything else follows: **the runtime lives in the package, and `.har/` is only what is yours.**

Pre-1.0, `har env init` copied the machinery into every repo — an 812-line `agent-slot.sh`, provisioning scripts, and lifecycle logic. Across three boilerplate profiles that was about 8,800 lines of template, 2,400 of them byte-identical duplicates. A bug fix had to land three times, and an already-adapted harness usually never got it.

In 1.0 the machinery runs once. `.har/` keeps config, stages, hooks, and plugins. The `./.har/*.sh` entry points are thin shims (`exec har env …`), so the CLI, MCP, and raw scripts write the same run records. Muscle memory does not change: `har env launch 1` and `./.har/verify.sh 1 --full` still work.

If you already have a harness, start at the [migration guide](/docs/guides/migrating-to-1-0/) — or copy the prompt above into your coding agent. How we shipped this is a separate piece: [The factory line](/blog/the-factory-line/).

## What you keep, what HAR manages

| Yours | Managed by HAR |
| --- | --- |
| `harness.env` — schema-validated config | Six ~35-line shims that `exec har env <kind>` |
| `stages.json` + `stages/*.sh` | Stock stage helpers |
| `hooks/*.sh` — lifecycle side effects | `manifest.json` — versions, migration history, drift checksums |
| Infra templates (compose, PM2) | Docs and agent guidance |

Customization has five sanctioned homes: config values, registered stages, [lifecycle hooks](/docs/guides/customization/#lifecycle-hooks), [plugins](/docs/guides/plugins/) (including [local ones](/docs/guides/local-plugins/)), and — if you genuinely want to own the runtime — [`har env eject`](/docs/guides/eject/). `har env doctor` validates the whole contract.

On this repository the migration took the main harness from 2,010 lines of shell (812 of them runtime) to 940. Machinery lines remaining: zero. `har env doctor` is green on all three harnesses here.

## What did not break

- `./.har/launch.sh 1` / `verify.sh 1 --full` / `teardown.sh 1`
- `har env …` and the MCP tools
- Existing `stages.json` ids and slot registries

Pre-1.0 vendored scripts keep working against the 1.0 CLI for a compatibility window — you get deprecation warnings, not a brick. Migrate when ready.

What 1.0 *does* retire: vendored-script internals, `add-stage --custom` (use a [local plugin](/docs/guides/local-plugins/)), shell functions in `harness.env`, and treating every drift warning as noise.

## What else shipped

Grouped from the [1.0.0 milestone](https://github.com/os-factory/har/milestone/1):

- **One runtime.** The harness implementation moved into `@osfactory/har` ([#234](https://github.com/os-factory/har/issues/234)). Installed scripts are shims with a pinned `npx` fallback ([#235](https://github.com/os-factory/har/issues/235)). CLI and MCP share the launch guard ([#233](https://github.com/os-factory/har/issues/233)).
- **Config, not shell.** `harness.env` is schema-validated `KEY=value` ([#230](https://github.com/os-factory/har/issues/230)). Profiles are capability manifests, not forked file trees ([#236](https://github.com/os-factory/har/issues/236)).
- **Verification as data.** One stage namespace, quick and full tiers ([#231](https://github.com/os-factory/har/issues/231)). `har env doctor` is the contract check ([#232](https://github.com/os-factory/har/issues/232)). Drift distinguishes “you edited this” from “upstream changed” ([#237](https://github.com/os-factory/har/issues/237)).
- **Extension points.** Lifecycle hooks ([#238](https://github.com/os-factory/har/issues/238)), `har env eject` ([#239](https://github.com/os-factory/har/issues/239)), and `har plugin create` for local plugins — which retires `add-stage --custom` ([#240](https://github.com/os-factory/har/issues/240)).
- **A real migration.** `har env maintain` detects the pre-1.0 shape, writes `MIGRATE-PROMPT.md`, and `--migrate` does the mechanical rewrite ([#241](https://github.com/os-factory/har/issues/241)). Agents read one instruction file: `AGENTS.md` ([#301](https://github.com/os-factory/har/issues/301)).

The full issue-by-issue list is on the [v1.0.0 GitHub release](https://github.com/os-factory/har/releases/tag/v1.0.0).

## Upgrade the CLI before the shims

If the `har` on `PATH` is older than 1.0, a 1.0 shim can `exec` back into that binary, which executes the shim again. That loop took a machine to 2,306 node processes. The shims now refuse (exit `86`) instead of forking forever.

```bash
npm install -g @osfactory/har@latest
```

In CI, put the runtime you mean to test on `PATH` **before** any `./.har/*.sh` step.

## Migrate

From the directory that owns `.har/`:

```bash
har env maintain
har env maintain --migrate   # after you have read the prompt
har env doctor
har env launch 1 && har env verify 1 --full
har env maintain --finalize --summary "Migrated to the 1.0 config surface"
```
